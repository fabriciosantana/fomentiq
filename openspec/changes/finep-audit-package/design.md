# Design

## Context

See `proposal.md` for motivation and `specs/finep-audit-package/spec.md` for required behavior. The live runner already has access to a terminal `IngestionRun`, PostgreSQL persistence and an S3-compatible artifact store, but selected provider excerpts are currently transient and must be captured if a future package is to be self-contained. Disposable run resources are removed after validation; the package must therefore be verified and copied to a separate private destination first.

## Goals / Non-Goals

**Goals:**
- Produce one versioned, deterministic package bound to the run, code SHA and approved manifest.
- Preserve original bytes and exact selected provider excerpts with content hashes and locators.
- Let an offline verifier decide integrity/completeness from package files alone.
- Make missing historical artifacts explicit and block false completeness.

**Non-Goals:**
- Reconstruct missing data for the already completed first run.
- Store audit packages in GitHub, public Git, the disposable run bucket, or logs.
- Add a public endpoint, UI, scheduler, microservice, queue or new third-party service.
- Include API/OAuth credentials, HTTP authorization headers, storage keys, or unfiltered raw provider payloads.

## Decisions

### D1 — Capture provider excerpts at request time

Persist the canonical excerpt manifest immediately before the provider call in the configured private audit directory, using a deterministic path derived from the ingestion run, call version, schema version and full canonical input digest. The existing `extraction_execution.input_digest` records that digest after the provider returns; no database schema change is planned. Compute the digest over canonical serialization of every provider-visible excerpt field (segment/document-version IDs, URL, title, page, section and exact text), so the existing execution identity resolves the exact manifest and detects metadata tampering. If repository inspection shows this linkage cannot be implemented without changing the database model, stop and request specific approval before proceeding. The manifest contains no provider authorization header. The exporter reads this immutable object; it must never call the selector again to recreate historical input.

Alternative: regenerate excerpts from PDFs after the run. Rejected because selector/code changes, document order and metadata can produce different input from what the provider saw.

### D2 — Make the package a deterministic ZIP with a canonical inventory

Use a versioned, documented ZIP layout with normalized relative paths and no symlinks or absolute paths. A `manifest.json` describes the run, source classification, package schema, completeness, required entries and per-entry byte length/SHA-256. A detached `SHA256SUMS` covers every payload file except itself; the manifest records its checksum. The verifier rejects duplicate paths, path traversal, unexpected files in strict mode, missing entries and checksum mismatch.

Proposed layout:

```text
manifest.json
authorization/manifest-sanitized.json
run/run-record.json
source/snapshots/<sha256>.<ext>
source/documents/<document-version-id>/<sha256>.pdf
extraction/provider-input-excerpts.json
extraction/schema.json
extraction/structured-result.json
extraction/field-history.json
extraction/evidence.json
review/field-review-matrix-template.json
inventory/SHA256SUMS
```

The ZIP contains only allowlisted fields. `storageKey` values are omitted; stable domain IDs, document hashes and safe public source references replace them. Query parameters are stripped/redacted where they could carry access values; preserve the original source artifact hash and record the redaction, rather than silently claiming byte identity for a transformed artifact.

### D3 — Define completeness as a graph of resolvable references

The exporter/verifier checks run → call version → extraction execution → field record → evidence → document version → included file references. Critical fields include their technical status even when `MISSING`; review outcomes belong to a separate package record and are not generated by export. A complete package requires every expected run artifact and provider excerpt object to resolve and every reference/hash/quote locator to validate. Absence, unsupported content or corruption yields `complete=false`, structured missing-item codes and a nonzero verification result.

For the historical run `2e859ec1-3916-4361-b10c-ac454b65061c`, the original database/storage and exact selected excerpts/raw response were deleted after the approved cleanup. It must not be retroactively repopulated from the fixture or selector replay; a retrospective bundle may contain the retained sanitized report and fixture references but must identify itself as partial and cannot satisfy live-run completeness.

### D4 — Keep factual review detached from extracted fields

Export a blank six-field review matrix template keyed to package ID/hash and source evidence. A later factual-review change defines the review outcomes and completed detached decision record. Neither exporter nor verifier alters `ExtractedField.validationStatus`, and export alone can never imply human approval.

Alternative: mutate the field's technical status when a reviewer approves it. Rejected because `VALIDATED` describes deterministic extraction validation and must remain distinct from human factual adjudication.

### D5 — Require a configured private directory and approved retention

The configured archive directory is outside the repository, disposable Compose volumes and manual-demo data. Require restrictive filesystem permissions, owner-readable access for the technical responsible and an explicit allowlist/group for reviewers; validate the real path and reject symlinks or paths within protected roots. No credentials are stored in configuration or package metadata. Keep local staging separate from the final package directory until the package has passed offline verification, then publish it atomically within the configured directory. The environment must preserve this directory when disposable run services are removed.

Approved initial retention: five years from package creation, with no automatic deletion. Any later deletion requires an explicit owner decision and a recorded deletion receipt. The implementation must record the retention policy version and creation date; it must not implement a cleanup timer.

### D6 — Verify offline with a separate command mode

The verifier consumes the ZIP and local package schema/verification code only. It must not initialize Spring persistence, Flyway, S3 clients, Finep connectors or OpenAI clients. Its deterministic output includes package ID, completeness, entries checked, reference checks and sanitized errors. Exit success means integrity/completeness only, not factual correctness or human approval.

## Risks / Trade-offs

- [Run cleanup may happen before export] → make export and private-copy verification explicit pre-cleanup gates; leave environment intact when either fails.
- [Exact excerpts may contain sensitive URL metadata] → allowlist request fields, redact only sensitive metadata with provenance, exclude credentials, and make redaction a completeness failure if it prevents exact request verification.
- [Object storage and PostgreSQL are not one transaction] → write the immutable excerpt object before the extraction execution record; if SQL recording or object upload fails, mark the run/package audit as incomplete and do not proceed to cleanup.
- [Public PDFs plus model excerpts can form a sensitive aggregate] → private destination, least privilege and owner-approved retention; never commit the package to Git.
- [Checksums alone do not prove authorship] → keep the package destination private and preserve the approved manifest/reference; consider signed manifests only if a later threat model justifies a signing-key lifecycle.
- [First run evidence was deleted] → permanently label any retrospective partial bundle and prohibit substituting fixture/reconstructed selector output for live excerpts.

## Migration Plan

1. Validate the configured private directory, access policy and approved five-year retention without adding credentials.
2. Capture the complete canonical provider input before invocation and use the existing extraction input digest to derive and later resolve its file; do not change database schema. Stop and escalate if that binding proves impossible without schema changes.
3. Export and verify package before isolated Compose teardown; remove only isolated service resources after the package is complete and atomically present in the configured directory.
4. Rollback disables package archival/export; do not delete already archived packages or existing source/run history.

## Approved Operational Policy

For this implementation, the owner has approved a configurable private filesystem directory outside Git and disposable Compose resources, read access restricted to the technical responsible and authorized reviewers, five-year initial retention, and no automatic deletion. The exact path and reviewer identities remain environment configuration and must be validated at runtime. Package completeness and the cleanup gate must fail closed when the path or access policy is absent or unsafe.
